# AI CONTEXT – NEON XO Admin app (`tic-tac-toe-admin`)

This file is written for AI assistants (and new developers). It describes the
whole admin project: purpose, architecture, data model, security model,
every important file, conventions, known limits and pitfalls. Read it fully
before changing code. The game has its own file with the same name
(`tic-tac-toe/AI_CONTEXT.md`) – read that too for the game side, the shared
Firestore data model and the full security rules.

---------------------------------------------------------------------------
## 1. What this is
---------------------------------------------------------------------------

- **Admin panel** for the NEON XO tic-tac-toe game. Flutter app, Android.
  University semester project.
- Package / Dart name: `neon_xo_admin`. Android applicationId:
  `com.example.neon_xo_admin`. Title "NEON XO Admin".
- Talks directly to the **same Firebase project as the game:
  `tic-tac-toe-4ab92`** (Firebase Auth + Cloud Firestore). There is no
  backend server.
- Firebase plan: **free Spark plan** → no Cloud Functions / Admin SDK.
  Consequences: the admin app cannot disable or delete another user's
  Firebase login; it manages Firestore data, and **Firestore security rules
  (stored in the GAME repo: `tic-tac-toe/firestore.rules`) enforce
  everything on the server**.
- All admins have **equal permissions** (no super-admin role, by decision).

---------------------------------------------------------------------------
## 2. Tech stack and versions
---------------------------------------------------------------------------

- Flutter, Dart SDK `^3.8.1`; lints `flutter_lints ^5.0.0`.
- Firebase: `firebase_core ^5.1.0`, `firebase_auth ^7.0.1`,
  `cloud_firestore ^7.1.0` (newer majors than the game app – fine, same
  project). No other runtime packages except `cupertino_icons`.
- `flutter_launcher_icons` (dev) with `assets/icon/admin_icon.png`.
- Android: compileSdk 36, minSdk 24, JVM 11, Kotlin DSL, google-services
  plugin; release signed with debug key.
- Only Android configured in `lib/firebase_options.dart` (ios/macos/linux/
  windows/web folders exist but would throw at Firebase init).
- No state-management library: `StatefulWidget` + `setState`,
  `StreamBuilder`, `FutureBuilder`. Services are plain classes created per
  screen (`final X _x = X();`).
- Charts are drawn with **plain Flutter widgets** (`widgets/simple_charts.dart`),
  no chart package.

## 4. App flow
---------------------------------------------------------------------------

1. `main()` → `Firebase.initializeApp` → `NeonXOAdminApp` (MaterialApp,
   `AppTheme.darkTheme`, home `AdminAppRoot`).
2. `AdminAppRoot` maps `FirebaseAuth.authStateChanges()` with `asyncMap` to
   a bool: signed in AND `admins/{uid}` exists with `role == 'admin'`.
   Otherwise it signs out. true → `AdminNavigationShell`, false →
   `AdminLoginScreen`.
3. `AdminLoginScreen`: email (max 254, live counter) + password, regex
   validation, "forgot password" → `sendPasswordResetEmail`. Calls
   `AdminService.login()`, which verifies the admin doc and back-fills
   missing name/email on old admin docs (best effort).
4. `AdminNavigationShell`: `LayoutBuilder`; width ≥ 900 → permanent
   sidebar, else AppBar + Drawer. Menu indexes:
   0 Dashboard, 1 Registered Users, 2 Player Profiles, 3 Statistics,
   4 Game History, 5 Manage Admins, 6 Activity Log. `_titles` list in
   main.dart and `_menuItems` in admin_drawer.dart must stay in the same
   order. Logout in drawer and on the dashboard AppBar.

## 5. Screens in detail
---------------------------------------------------------------------------

**Dashboard** – `StatsService.getOverview()` (FutureBuilder, refresh button +
pull-to-refresh): total players, blocked players, total games, wins, losses,
draws. "Recent Admin Activity" = `AdminLogService.recent(limit: 5)` stream.

**Registered Users (userscreen.dart)** – `UserService.getUsers(limit)`
(newest first by `createdAt`, 25 per page, "Load more" raises the limit and
recreates the stream). Counts via `getCounts()` (count queries). Search
filters loaded players only (name/email/phone/UID). Per player: View
profile dialog, Edit (display name only – email/phone are tied to the
player's login and offline profile, shown read-only), Send password reset,
Block/Unblock (confirmation), Delete (confirmation + checkbox "Also delete
their game history", default on; note about removing the login in the
console). There is intentionally NO "add player" (a Firestore-only profile
without a login is useless).

**Player Profiles** – `user_profiles` ordered by `updatedAt` desc, 25 per
page; each card streams the matching `users` doc for phone; edit bio
(max 200 in UI, rules allow 40 from the game but admins are not limited),
delete bio (`FieldValue.delete()`). Both actions are logged.

**Statistics** – summary cards (overview aggregates), charts:
games per day (last 14 days, query `completedAt >= start`), results split
(sum of wins/losses/draws), most active players (top 5 by gamesPlayed).
Player list: `player_stats` ordered by `gamesPlayed` or `wins`, paged;
"Win Rate" sorts loaded rows on the device.

**Game History** – `game_history` ordered by `completedAt` desc, 30 per
page; totals from count queries (`resultForPlayer1 == win/loss/draw`);
search + result/difficulty filters apply to loaded games.

**Manage Admins** – Create New Admin form (name, email ≤ 254 with counter,
temporary password ≥ 8, confirm). If the email already has a login and
belongs to a player (`users` where email ==), offers to grant admin access
to that account instead. "Add existing account by UID" (ExpansionTile).
Admin list (name, email, UID, YOU badge), search, send password reset,
remove access (cannot remove the last admin; removing yourself signs you
out).

**Activity Log** – `admin_logs` ordered by `createdAt` desc, 30 per page,
search + action filter dropdown, tap for detail dialog. Read-only.

## 6. Key technical solutions
---------------------------------------------------------------------------

**Creating admins without a server** (`AdminService.createAdmin`): a second
`FirebaseApp` named `admin-account-creator` is initialised with the same
options; `FirebaseAuth.instanceFor(app: secondary)
.createUserWithEmailAndPassword` creates the login without touching the
current admin's session. Then the CURRENT admin writes `admins/{newUid}`
(rules allow admins). On any failure after creation the new login is
deleted again (`_rollBack`). The secondary auth is always signed out in
`finally`. `email-already-in-use` → `EmailAlreadyRegisteredException`
(with player uid/name if found in `users`).

**Blocking** (`UserService.setUserBlocked`): batch { update `users/{uid}`:
isBlocked, status, blockedAt/blockedBy (or FieldValue.delete on unblock),
updatedAt; delete `leaderboard/{uid}` when blocking }. The GAME reacts
immediately via its snapshot listener (signs the player out). Rules deny
blocked players all writes.

**Deleting a player** (`UserService.deletePlayer`): batch { set
`deleted_users/{uid}` tombstone, delete `users`, `player_stats`,
`leaderboard`, `user_profiles` }, then optional `game_history` deletion in
pages of 400 (`where player1Uid == uid`). The Firebase Auth login remains
(Spark plan); the game refuses it because the profile is gone.

**Renaming** updates `users.name` and, if present, `leaderboard.name`
(the rules require the leaderboard name to equal `users.name`).

**Activity log** (`AdminLogService.log`): every mutating action writes
`admin_logs` {action (AdminAction.name), adminUid, adminEmail, targetUid,
targetName, details, createdAt: serverTimestamp}. Never throws (a failed log
must not undo the action). Rules: admins may create (adminUid must be their
own uid), never update/delete. Logged actions: adminCreated, adminAdded,
adminRemoved, playerBlocked, playerUnblocked, playerDeleted, playerRenamed,
bioEdited, bioDeleted, passwordResetSent.

**Keeping reads low (Spark: 50k reads/day)**: lists use `.limit(n)` with
"Load more"; totals use `count()` and `aggregate(sum(field))` which cost one
read per 1000 docs. IMPORTANT: each `sum()` is a separate aggregate query –
combining several fields in one aggregate needed a composite index and
failed with FAILED_PRECONDITION, so it was split. All current queries use a
single field and need no composite index.

## 7. Shared Firestore data model (short)
---------------------------------------------------------------------------

`users/{uid}` (name, email, phone, createdAt, emailVerifiedAt, isBlocked,
status, blockedAt, blockedBy, updatedAt) · `player_stats/{uid}`
(gamesPlayed, wins, losses, draws, email) · `game_history/{auto}`
(player1Uid, player1Email, opponentType, opponentName, difficulty,
resultForPlayer1, completedAt) · `user_profiles/{uid}` (bio, phone,
updatedAt) · `leaderboard/{uid}` (public name + totals) · `admins/{uid}`
(role 'admin', name, email, createdAt, createdBy) · `admin_logs/{auto}` ·
`deleted_users/{uid}` (tombstone). Full field list and rules: see the game's
AI_CONTEXT.md §8–9 and `tic-tac-toe/firestore.rules`.

Rules that matter for this app: admin = `admins/{auth.uid}.role ==
'admin'`; admins can read everything they need, update/delete players' data,
write `admins` (email ≤ 254), `deleted_users`, create (not edit) `admin_logs`,
rename/delete `leaderboard` entries. Bootstrap: the first admin must be
created by hand (Auth console + `admins/<uid>` doc with `role: "admin"`).

## 8. Conventions for changes
---------------------------------------------------------------------------

- Colours: always `AppTheme.*` (background #0B0B2B, surface #171F35,
  cardSurface #141A32, purple #7B2FF7, neonCyan #00E5FF, neonPink #FF2BD6,
  neonYellow #FFD600). Exception: `admin_login_screen.dart` keeps its own
  slightly different private palette for the login look.
- New lists over growing collections: page with `.limit()` +
  `LoadMoreButton`; keep the stream in state (`late Stream`, recreated in
  `_loadMore`), never create streams inside `build`.
- New totals: use `count()` / single-field `sum()` aggregations.
- Every new mutating admin action: call `AdminLogService().log(...)` and add
  an `AdminAction` value if needed.
- Any new collection/field written: update `tic-tac-toe/firestore.rules`
  and redeploy from the GAME folder (`firebase deploy --only
  firestore:rules`).
- Email limit everywhere: 254 (`AdminService.maxEmailLength`), visible
  counter on input fields. Same in the game and the rules.
- Errors to the user: `SnackBar` with `e.toString().replaceFirst
  ('Exception: ', '')`. Confirmation dialogs for destructive actions.
- Debug prints only under `kDebugMode`.
- Files use Windows CRLF line endings (repo on OneDrive) – keep CRLF.
- Adding a screen: add the widget, a `case` in
  `_AdminNavigationShellState._getSelectedScreen`, a title in `_titles`,
  and a `_MenuItem` in `AdminDrawer._menuItems` at the same index.

## 9. Known limitations / technical debt
---------------------------------------------------------------------------

- Cannot disable/delete other users' Firebase logins (Spark plan); deleted
  players' logins must be removed by hand in Firebase console →
  Authentication.
- Search/filter on paged screens only covers loaded items.
- Dashboard/statistics totals are fetched once (refresh button), not live.
- No re-authentication before destructive actions (decided not to add).
- Only Android configured (web version was considered and declined).
- `dashboard_card.dart` is unused legacy.
- No automated tests yet (only the default template test).
- `DropdownButtonFormField(value: ...)` may show a deprecation hint on newer
  Flutter (`initialValue`).

## 10. Setup / commands
---------------------------------------------------------------------------

```
flutter pub get
flutter analyze
flutter run
```
Rules are deployed from the game folder, not from here.
First admin: create login in Firebase console → Authentication, then add
Firestore doc `admins/<uid>` with `role: "admin"`; more admins can then be
created in the app (Manage Admins → Create New Admin).
